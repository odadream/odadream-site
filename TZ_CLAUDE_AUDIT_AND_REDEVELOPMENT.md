# ТЗ для Claude Code: аудит и план доработки odadream.art

## Режим задачи

Проведи **аудит перед переработкой**, а не редизайн вслепую. На этом этапе не удаляй код, контент, медиа или CMS-данные, не меняй `main` и не деплой сайт. Сначала подготовь доказательный план: что оставить, адаптировать, заменить или вывести из публичного интерфейса.

Рабочий репозиторий: `D:\YandexDisk\_ODA2\Сайт\odadream-site`.

Перед работой обязательно прочти `CLAUDE.md`, `CONTENT-SCHEMA.md`, `content-keeper/STRUCTURE-CURRENT.md`, `content-keeper/STRUCTURE-PROPOSED.md` и `content-keeper/BACKLOG.md`. `CONTENT-SCHEMA.md` — источник истины для контентной модели.

## Контекст и задача сайта

ODA.dream — не digital-агентство, neurotech-стартап или wellness-сервис. Это художественная практика, в которой человеческое состояние, отношения между людьми и коллективная динамика становятся материалом произведения. EEG, biosignals, computer vision, generative systems, свет и звук — инструменты, а не главный предмет коммуникации.

Главный сценарий сайта:

`получатель персонального outreach-письма → кликает ссылку → за 10–20 секунд понимает художественную практику → за 1–3 минуты видит реальные работы и доказательства → находит подходящий формат сотрудничества / контакт`.

Текущий сайт — текстовая SPA со spatial-навигацией Blossoming Lotus. Пользователь считает её недостаточно визуальной и плохо адаптированной к мобильным устройствам. Цветущий лотос, лабиринтная навигация и необходимость изучать интерфейс не должны быть основой нового публичного опыта.

Цель — превратить сайт в visual-first, mobile-first портфолио современной художественной практики, не выбросив накопленные контент, медиа, доказательства и полезную техническую основу.

## Целевой публичный опыт

### Позиционирование

Основной тезис должен быть понятен без технического жаргона:

> ODA.dream creates artworks from human states, relationships and collective behaviour.

Допустимый краткий вариант: `Human state as artistic material.`

На первом экране допустима маленькая поясняющая строка:

`Performance · Installation · Neurotechnology · Generative Systems`

### Информационная архитектура

Ориентир для нового верхнего уровня:

- `Works`
- `Commissions`
- `About`
- `Contact`
- `Research` — только если после аудита он нужен отдельной аудитории.

Нужны короткие URL-входы из персональных писем. Они могут быть отдельными страницами или представлениями одной контентной модели, но не должны выглядеть как разные бренды:

- `/art` — кураторы, музеи, фестивали;
- `/commissions` — бренды, девелоперы, event/creative agencies;
- `/live` — сценические продюсеры и performance-контекст;
- `/research` — университеты, labs, art & science.

Главная должна вести по последовательности:

`сильный визуальный hero → тезис → 4–6 сильнейших работ → commissions → доказательства → простой контакт`.

Возможная смысловая структура работ: `ONE / TWO / MANY` — индивидуальное состояние, отношения двух людей, коллективное состояние. Не принимай её как обязательную без проверки реального корпуса работ; оцени, действительно ли она упрощает понимание практики.

### Визуальный и мобильный принцип

- Visual first: по ощущению 70–80% медиа и 20–30% текста.
- Hero — реальные люди, сцена, взаимодействие, изменение пространства, аудитория; не абстрактная декоративная generative-графика.
- Contemporary art institution + cinematic performance documentation, не sci-fi UI и не tech-startup.
- Нейтральный UI; цвет приходит из работ и документации.
- Проектировать от 360 px; не переносить десктопную сложность на мобильный.
- Никаких hover-only действий, непонятных горизонтальных галерей, мелких tap-target, обязательного zoom или запутанной пространственной навигации.
- Мобильный первый маршрут: `video → thesis → strongest works → commissions → proof → contact`.
- Видео: muted autoplay допустим только с poster/fallback, адаптивной загрузкой и контролем веса. Не ухудшать LCP ради декоративного ролика.

## Что требуется исследовать

### 1. Снимок текущего продукта

Запусти сайт локально, пройди его как новый посетитель на desktop и mobile viewport (минимум 360 px и один широкий desktop). Сделай скриншоты ключевых состояний и проверь реальные маршруты, URL, загрузку медиа, языки, меню, lightbox, контакты и deep links.

Разбери фактические точки входа в коде:

- приложение и layout: `src/App.tsx`, `src/components/*`, `src/index.css`;
- навигация и URL-состояние: `src/context/NavigationContext.tsx`, `src/hooks/*`;
- Lotus grid / map: `LotusGrid`, `LotusMap`, `LotusSidebar`, `HeaderTabs`, `Breadcrumbs`;
- контентный граф и CMS: `src/content/`, `src/utils/contentLoader.ts`, `src/utils/contentProcessor.ts`, `src/utils/frontmatter.ts`, `src/constants.ts`, `src/types.ts`;
- медиа и доказательства: `src/data/media.ts`, `src/utils/provenance.ts`, `ProvenancePanel`, `data/registry/`;
- SEO/аналитика: `src/utils/metaTags.ts`, `public/sitemap.xml`, `src/analytics/`.

Не делай выводы только по именам файлов: подтверждай их просмотром интерфейса и конкретными местами кода.

### 2. Инвентаризация для решения «оставить / изменить / убрать»

Для каждого значимого элемента подготовь таблицу с колонками:

| Элемент | Где реализован | Польза для новой цели | Решение | Способ миграции / риск |
|---|---|---|---|---|

Решения только из следующего набора:

- **Оставить** — сохраняется практически без изменения публичного назначения.
- **Сохранить как инфраструктуру** — остаётся в коде/данных, но не диктует новый UI.
- **Адаптировать** — остаётся, но требует конкретной переработки UX/UI/API.
- **Заменить** — публичный механизм меняется, с поэтапной миграцией и совместимостью.
- **Скрыть из публичного интерфейса** — остаётся доступным для разработки или архива, но не участвует в ключевом маршруте.
- **Удалить позднее** — только после подтверждённой миграции и проверки ссылок.

Обязательно оцени:

1. Lotus grid, Blossom/lotus-метафору, Lotus map, sidebar, header tabs, breadcrumbs и query-param routing.
2. Markdown/file-based CMS, EN/RU-разделение, content graph, wiki-links, provenance и registry data.
3. Существующие карточки работ, события, проекты, медиа, изображения, видео, PDF, доказательства, awards/press/partners/clients.
4. Темы, design tokens, Framer Motion, lightbox и текущую CSS-архитектуру.
5. Генерацию SVG-фонов и способы, которыми контент получает обложки.
6. Vite/static hosting/GitHub Pages, deep-link ограничения и OpenGraph/SEO.
7. Производительность, accessibility, responsive layout, keyboard/focus, `prefers-reduced-motion`, semantic HTML и image/video loading.
8. Существующие documentations и миграции в `content-keeper/`; не дублируй уже принятые решения без объяснения различия.

### 3. Аудит контента и медиа

Не пытайся на этой стадии переписать все 154+ узла. Вместо этого:

- выдели 4–6 работ, которые имеют наилучшие визуальные материалы, ясный художественный тезис и подтверждённый контекст;
- отдельно обозначь работы, пригодные для `Commissions`, `Live`, `Research` и art/institutional-входа;
- найди контент, который следует оставить доступным глубоко в архиве, но не ставить на первую линию;
- выяви критические контентные пробелы: hero reel, project loops, качественные фотографии, короткие тезисы, English copy, proof/press, корректные captions, обложки;
- проверь, какие форматы медиа реально поддерживаются и безопасны для mobile/production;
- перечисли точные файлы и нужные материалы, но не выдумывай факты, награды или кейсы.

Особый кандидат на флагманский case study — **Interference of Realities**. Проверь фактическую наполненность его страницы и медиа, прежде чем закреплять это решение.

## Ограничения и сохранность

- Не удаляй `src/content/`, `data/registry/`, `src/data/media.ts`, `public/media/`, `public/images/`, scripts и content-keeper документы в рамках аудита.
- Не редактируй вручную производные registry/контентные данные, если документация указывает синхронизационный процесс.
- Любая новая навигация должна сохранить старые внешние `?id=` ссылки: через adapter, redirect или подтверждённые canonical URLs. Составь список рисковых ссылок.
- Статический хостинг и двуязычность остаются обязательными.
- Не добавляй CMS, backend или тяжёлую библиотеку без аргументированного сравнения с текущей file-based моделью.
- Не делай «services / solutions / products» ключевым языком интерфейса. Внешние заказы оформляются как `Commissions`.
- Не изображай EEG как чтение мыслей и не делай его главным героем коммуникации.

## Артефакты результата

Создай в репозитории документ `content-keeper/AUDIT_REDEVELOPMENT_VISUAL_SITE_YYYY-MM-DD.md` и приложи/сошлись на папку со скриншотами. Документ должен содержать:

1. Executive summary: 8–15 пунктов, что именно мешает нынешнему сайту работать после outreach и какие сильные основы уже есть.
2. Матрицу «оставить / адаптировать / заменить / скрыть» по интерфейсу, архитектуре, контенту и техническому стеку.
3. Аудит desktop/mobile с доказательствами: screenshots, размеры viewport, конкретные компоненты/строки или CSS-правила.
4. Карту текущего пользовательского пути и рекомендуемый новый путь.
5. Целевую IA и маршрут для `Works`, `Commissions`, `About`, `Contact`, при необходимости `Research`; включая URLs и стратегию обратной совместимости для `?id=`.
6. Список флагманских работ и недостающих материалов с уровнем уверенности и ссылкой на исходные файлы.
7. Предлагаемую архитектуру реализации: какие компоненты/утилиты переиспользуются, какие новые нужны, какие изолируются как legacy.
8. Accessibility/performance/SEO checklist с измеримыми acceptance criteria.
9. Пошаговый roadmap: discovery → information architecture → visual system → prototype → migration → QA → deployment. Для каждого этапа: зависимости, риск, критерий готовности.
10. Список решений, которые нельзя принять без Ольги и Далера: выбор флагманских работ, право на использование медиа, финальная EN/RU формулировка, контактные сценарии, бренд-материалы.

В конце приложи **implementation backlog** из небольших задач, каждая с приоритетом `P0/P1/P2`, оценкой сложности, затрагиваемыми файлами и проверкой результата. Не выполняй этот backlog до подтверждения владельцев проекта.

## Критерии качества аудита

Аудит считается готовым, если:

- решение по каждому ключевому элементу аргументировано целью сайта, а не личным вкусом;
- рекомендации различают UI, данные, контент и техническую инфраструктуру;
- сохранён конкретный план миграции без потери CMS-данных, медиа и старых ссылок;
- мобильный сценарий проверен, а не упомянут формально;
- рекомендации выполнимы в существующем React + TypeScript + Vite проекте;
- ясно, какие решения уже можно реализовывать, а какие требуют ответа владельцев;
- выполнены `npm run assets:map`, `npm run audit`, `npm run build`, а результаты и существующие сбои честно зафиксированы без попытки замести их исправлениями вне задачи.

## Не является результатом этой задачи

- готовый production-редизайн;
- массовое перемещение/переписывание контента;
- удаление Lotus/CMS-кода;
- смена платформы, CMS или хостинга;
- деплой или коммит без отдельного разрешения.
