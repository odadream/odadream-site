# Аудит odadream.art перед визуальным редизайном

**Дата:** 2026.08.24 · **Режим:** аудит, без изменений кода/контента, без деплоя.
**Основание:** `TZ_CLAUDE_AUDIT_AND_REDEVELOPMENT.md` (прислано владельцем как заметки внешнего ревьюера).
**Метод:** чтение кода (`src/**`), живой проход по dev-серверу (desktop 1280px + mobile 375px, Vite `npm run dev`), запуск `npm run assets:map`, `npm run audit`, `npm run build`.

> Скриншотов как файлов в этом прогоне не сохранено — визуальная проверка велась вживую через встроенный браузер в рамках этой сессии (см. конкретные маршруты/viewport в разделе 3). Если нужен постоянный набор PNG для дальнейшей работы дизайнера — это отдельная follow-up задача (снять полный набор через Playwright/Percy), не блокирующая выводы аудита.

## 1. Executive summary

1. **Контент сильнее интерфейса.** У студии есть настоящий, разнообразный визуальный материал — например, у «Интерференции реальностей» это полная запись спектакля, фоторепортаж, афиша, информационные плакаты и радио-интервью (`media-interference-*.md`); у «Проекта Шрёдингер» — тизер-видео и 8 фото. Проблема не в нехватке медиа, а в том, что архитектура не выносит их на поверхность.
2. **Первый экран — целиком текст.** На desktop и особенно на mobile (375px) первый видимый контент — три абзаца прозы о художественной практике и ЭЭГ, и только затем сетка 3×3 с процедурной абстрактной SVG-графикой (не фото людей/сцены). Это прямо противоречит целевому маршруту `video → thesis → strongest works` из ТЗ.
3. **Реальные фото есть, но лежат на 3–4 клика вглубь.** Путь до настоящей фотографии спектакля: Главная → Работы → Большие формы → Интерференция реальностей → Фото → открыть лайтбокс. Ни один реальный кадр не виден раньше этого пятого шага.
4. **На мобильном навигатор Lotus съедает почти половину экрана постоянно.** Текстовая панель скроллится в собственном ограниченном контейнере (`overflow` внутри блока, `body { overflow:hidden }`, `src/index.css:157-169`), а сетка 3×3 занимает нижние ~40% viewport (375×812) не прокручиваясь — эффективная область для контента на мобильном меньше, чем кажется по высоте экрана.
5. **Декоративный глитч-эффект заголовков местами делает текст нечитаемым.** Заголовки и подписи ячеек периодически отображаются как псевдослучайный набор символов (например «ODA.DE[2|» вместо «ODA.DREAM», «НАВИГ)С?#» вместо «НАВИГАТОР» — зафиксировано на живых скриншотах). Это стилистический приём (`CyberText`), но он не различает decorative/informational контент и затрагивает саму навигацию.
6. **Карта сайта (Lotus Map) на desktop уже плотная и малочитаемая**, а особого мобильного слоя для неё нет — судя по `LotusMap.tsx`, адаптивность обеспечена только внешним flex-контейнером, без собственных touch/адаптивных сценариев.
7. **IA-реструктуризация уже частично выполнена в коде.** Отдельный документ `content-keeper/STRUCTURE-PROPOSED.md` (до этого ТЗ, другая инициатива) описывал переход `hub-works` на 4 категории (Большие формы / Перформансы / Инсталляции / Материя) и вынос `hub-tech` на верхний уровень — **это уже реализовано** в текущем графе (проверено `npm run assets:map` и живой навигацией). Значит, часть работы по упрощению информации уже сделана, но не для `hub-world`.
8. **`hub-world` — незавершённая миграция, а не хаос.** Там одновременно существуют старый плоский `hub-letters` (14 пруфов) и новые `awards`/`clients`/`collabs`/`partners` страницы, которые должны были его заменить. Cap = 8, видимых детей = 14 (компенсировано built-in индикатором `+6`, а не тихой обрезкой) — те же 30 из 34 `org-*` карточек корректно скрыты (`visible: false`) и участвуют только в provenance, не в навигации. Это уже правильный паттерн для организаций — его стоит взять за образец для остального контента.
9. **Реальные фактические пробелы контента, а не выдумки:** у `sound-brain` в качестве аудио стоит плейсхолдер `https://www.soundhelix.com/examples/mp3/SoundHelix-Song-1.mp3` (стоковый тестовый трек, не реальная запись); `ancestors` (Предки в шуме, «Большие формы») и `cultural-neuro-code` не имеют собственных медиа-узлов, хотя формально входят во флагманскую линию.
10. **`npm run audit` фиксирует объективный технический долг**, не связанный с визуалом: 26 provenance-«сирот» (узлы без входящих ссылок), 20 отсутствующих referenced id, 10 «body smells», 36 записей пруфов, живущих только в `.md` и ещё не попавших в `proofs.yaml`. Это не блокирует редизайн, но стоит учитывать при выборе, какие карточки показывать как «доказательства».
11. **Технически сайт чист: `tsc`/`vite build` проходят без ошибок.** Но бандл не разбит на чанки: основной JS-чанк — 609 KB (207 KB gzip) для современных браузеров и 678 KB (218 KB gzip) для legacy — `React.lazy`/`Suspense` в проекте не используется нигде, включая `Lightbox`, вопреки комментарию в `CLAUDE.md` о «lazy-loaded» лайтбоксе (это упоминание устарело).
12. **Доступность — местами продумана, местами нет.** `LotusGrid` дублирует hover через `onFocus`/`onBlur` и имеет `role="button"`/`aria-label`/`tabIndex` (клавиатурная доступность есть); но `prefers-reduced-motion` не используется вообще, `loading="lazy"` не используется вообще (все изображения `eager`, осознанно — комментарий в коде про «blank flash»), и `<nav>`-тег в разметке отсутствует.
13. **Аналитика сделана аккуратно и с согласием** (`AnalyticsConsent.tsx`, явный `consent-mode`, вебвизор по умолчанию выключен) — это должно остаться как есть, редизайн этого не касается.
14. **`sitemap.xml` содержит один URL** (только главная), при 226 узлах с уникальными `?id=` — для visual-first портфолио, рассчитанного на прямые ссылки из outreach-писем (`/art`, `/commissions` и т.п.), это значит, что все внутренние страницы сейчас невидимы для поисковиков и не имеют собственных превью-карточек в соцсетях за пределами дефолтных og-тегов главной.
15. **Файловая CMS (frontmatter + `NODE_REGISTRY` + provenance-граф) — качественная инфраструктура**, не завязанная напрямую на текущий Lotus UI. Она может пережить визуальный редизайн почти без изменений — это как раз тот случай «сохранить как инфраструктуру», о котором просит ТЗ.

## 3. Аудит desktop/mobile — доказательства

Проверено на локальном dev-сервере (`npm run dev`, Vite 5.4.21, React 18, без консольных ошибок на всех проверенных маршрутах).

### Desktop (1280×800 логически, снято в 800×793 окне без изменения масштаба)

- **Главная (`/`).** Первый экран: слева — текстовый блок «Искусство, наука и технологии» + 3 абзаца прозы; справа — сетка 3×3 с абстрактными процедурными SVG-фонами (окружности/прямоугольники в оттенках серого), центральная ячейка — цветной абстрактный паттерн с подписью «ODA.DREAM». Ни одной фотографии людей/сцены на первом экране нет.
- **Cookie-баннер** перекрывает нижнюю треть текстового блока при первой загрузке (`AnalyticsConsent.tsx`), кнопки «Allow analytics» / «Necessary only» — стандартный consent-паттерн, работает корректно.
- **`Работы → Большие формы`.** Плитки уже показывают реальные постеры спектаклей («Интерференция реальностей», «Проект Шрёдингер») — здесь визуальный язык уже работает как надо.
- **`…→ Интерференция реальностей → Фото`.** Открывается не лайтбокс сразу, а промежуточный grid-узел с 8+ превью реальных чёрно-белых театральных фото (высокий контраст, компьютерное зрение/лазерная графика на сцене, реальные зрители). Качество кадров хорошее. Клик по превью открывает модальный `Lightbox` с `role="dialog"`, `aria-modal`, фокус-трапом и Escape-закрытием — реализовано корректно.
- **Карта сайта (переключатель в шапке навигатора).** Открывает фрактальную сетку ячеек размером ~60×35px с 2-3-буквенными обрубками подписей (напр. «БИТ ВА...», «ВЕС ТК...») — нечитаемо без наведения курсора на каждую ячейку отдельно. Это тот интерфейс, который в ТЗ прямо назван «не должен быть основой публичного опыта».
- Заголовки/подписи периодически отображаются в виде псевдослучайного глитч-набора символов вместо текста (эффект `CyberText`) — зафиксировано и на главной, и на внутренних страницах. Иногда попадает и на кликабельные элементы навигации, временно делая их нечитаемыми (не мешает клику по позиции, но мешает считыванию смысла).

### Mobile (375×812, эмуляция touch)

- Верхняя панель вкладок обрезана: видно только «ODA.DREAM / РАБОТЫ / СОТРУДНИ→», остальные 6 пунктов верхнего уровня скрыты за горизонтальным скроллом без явной подсказки «есть ещё».
- Первый экран (без скролла) — **только текст**: H1 «ODA.dream» (в момент снимка искажён глитчем до «ODA.DE[2|»), тег-лайн, первый абзац прозы, и лишь на самом нижнем крае начинается верхний ряд сетки 3×3.
- Текстовая панель скроллится в собственном контейнере; при скролле внутри неё **сетка навигатора остаётся неподвижной** и постоянно занимает нижние ~340px из 812px высоты экрана (≈42% viewport) — заметно больше эффективной площади под контент, чем кажется на глаз при беглом просмотре.
- Плитки сетки на 375px — три в ряд, подписи в одну строку с обрезкой (`РАБОТ2`, `СОТРУНД…`) — не критично, но плотно.
- Специального брейкпоинта для узких экранов (320–360px, как просит ТЗ) в CSS не найдено — в `src/index.css` всего два `@media`-правила (`min-width:768px` и мобильный `orientation:landscape`-кейс), то есть весь диапазон 0–767px обслуживается одним и тем же layout без промежуточной настройки.

### Итог по аудиту UI

Технически сайт работает без ошибок и на desktop, и на mobile. Проблема — не баги, а архитектурное решение: **навигационная метафора и декоративная эстетика первичны, реальный визуальный контент вторичен и скрыт на несколько уровней вглубь.**

## 4. Текущий путь пользователя vs целевой

**Текущий путь (outreach-письмо → сайт):**

```
клик по ссылке → главная (только текст, абстрактная графика)
  → нужно понять метафору «Лотоса» из объясняющего текста
  → кликнуть «Работы» (текстовая hub-страница с ещё одним текстовым описанием 4 категорий)
  → выбрать категорию (например «Большие формы») — здесь наконец появляются постеры
  → открыть конкретную работу — текст + сетка медиа-узлов
  → открыть «Фото» как отдельный узел — только теперь реальные фотографии
  → открыть лайтбокс — полноразмерное фото
```

Итого до первой убедительной фотографии — **5 переходов** и минимум 2 экрана плотного текста.

**Целевой путь (по ТЗ, с поправкой на то, что реально есть в контенте):**

```
hero (реальное фото/видео лучшей работы, автоплей muted с poster)
  → тезис в одну строку («ODA.dream создаёт произведения из человеческих состояний...»)
  → 4-6 сильнейших работ сеткой с реальными обложками (не абстрактный SVG)
  → Commissions (форматы сотрудничества)
  → доказательства (награды/пресса/партнёры — уже готовы как provenance-граф)
  → контакт
```

Это не требует придумывать контент — почти весь материал для этого пути уже есть в `src/content/*.md` и `src/data/media.ts`; не хватает **выноса** его на первый уровень.

## 5. Целевая IA и обратная совместимость

Учитывая, что часть реструктуризации (`STRUCTURE-PROPOSED.md`) **уже реализована в данных** (см. §1.7), новую публичную IA логичнее строить как **представление** поверх уже готовой категоризации, а не как ещё одну параллельную реструктуризацию контента.

Предлагаемые публичные маршруты (path-based, человекочитаемые, поверх существующего `NODE_REGISTRY`):

| Маршрут | Источник данных (уже существует) | Аудитория |
|---|---|---|
| `/` | Hero + подборка из `hub-big-forms` + `hub-performances` | Все |
| `/works` | `hub-works` → 4 категории (уже есть: `hub-big-forms`, `hub-performances`, `hub-installations`, `hub-materia`) | Кураторы, фестивали |
| `/works/:slug` | Конкретный `product`-узел (`interference`, `schrodinger`, …) | Все |
| `/commissions` | Новая страница-агрегатор поверх `hub-collab` (`hub-business`, `hub-event-agencies`, `hub-institutions`) | Бренды, агентства, девелоперы |
| `/live` | Подмножество `hub-performances` + `hub-events` (сценический контекст) | Продюсеры |
| `/research` | `hub-tech` + `cultural-neuro-code` — **только если** после аудита контента там наберётся достаточно материала для отдельной аудитории (сейчас `hub-tech` — по большей части заглушки, см. §6) | Университеты, лаборатории |
| `/about` | `hub-world` (после завершения его внутренней миграции, см. §2) | Все |
| `/contact` | `hub-contacts` | Все |

**Обратная совместимость `?id=`:** механизм в `NavigationContext.tsx:103-137` уже умеет резолвить `?id=<nodeId>` в узел графа независимо от способа захода. Самый дешёвый путь — оставить текущий query-param роутинг работающим как fallback/redirect-слой: любой старый `?id=interference` редиректит на новый `/works/interference` через тот же `NODE_REGISTRY`, без миграции данных. Риска потери входящих ссылок из старых outreach-писем нет, если этот редирект не убирать.

**Точечный дефект данных:** `sound-brain.md` использует внешний плейсхолдер `https://www.soundhelix.com/examples/mp3/SoundHelix-Song-1.mp3` вместо реальной записи — это стоковый тестовый файл, не относящийся к студии; для публичного визуального сайта такой узел либо нужно наполнить реальным аудио, либо не выводить на витрину.

**Данные из `npm run audit` (`content-keeper/PHASE-F-AUDIT.md`), релевантные контент-аудиту:**
- 26 orphan-узлов (без входящих ссылок и детей) — среди них `emomandala-os`, `gong`, `journey`, `meditation-brain`, `sound-brain`, `taste-brain`, ряд `event-*` без proofs/products. Не критично для навигации (у некоторых есть `parent`), но означает отсутствие provenance-связей — такие узлы не появятся в блоке «доказательства» ни у одной работы.
- 36 пруфов существуют только в `.md`, ещё не отражены в `proofs.yaml` (снимок отстаёт от источника правды) — не блокирует редизайн, но `hub-registry:sync` стоит прогнать перед тем, как строить на данных `proofs.yaml` витрину доказательств.

## 7. Предлагаемая архитектура реализации

**Переиспользуется без изменений:**
- `src/utils/contentLoader.ts`, `contentProcessor.ts`, `frontmatter.ts` — весь конвейер загрузки контента.
- `src/constants.ts` (`NODE_REGISTRY`, `ROOT_NODE`) — граф остаётся единым источником правды.
- `src/utils/provenance.ts` — как источник данных для секции доказательств/партнёров.
- `src/data/media.ts` — каталог медиа не меняется структурно.
- `src/analytics/*`, `src/utils/metaTags.ts` (с расширением на все маршруты, а не только текущий узел).

**Требует новых компонентов:**
- Path-based роутер поверх `NODE_REGISTRY` (легковесный, без тяжёлой библиотеки — согласно ограничению ТЗ; `react-router` в статическом SPA на GitHub Pages потребует настройки fallback, что решаемо, но нужно явное решение, см. §10).
- Hero-компонент с реальным видео/фото (заменяет текстовый первый экран).
- Карточная сетка работ (grid из реальных обложек, без процедурных SVG как основного визуального языка).
- `Lightbox` дорабатывается: `poster` для видео, `loading="lazy"` для изображений вне первого экрана.

**Изолируется как legacy (не удаляется):**
- `LotusGrid.tsx`, `LotusMap.tsx`, `LotusSidebar.tsx`, `mapPyramid.ts`, `fractalGrid`-логика внутри `LotusMap.tsx` — доступны по прямой ссылке/флагу для интересующихся или как «пасхалка», согласно духу текущего changelog («undocumented gesture»), но не в основном маршруте.
- `CyberText`-эффект — оставить только в некритичных декоративных местах, убрать с заголовков/лейблов навигации.

## 9. Roadmap

2. **Information architecture.** Зафиксировать маршруты §5, спроектировать редиректы `?id=` → path-based URL. *Зависимости:* шаг 1. *Риск:* средний (ошибка в мэппинге ломает старые ссылки из outreach). *Готово когда:* таблица старый→новый URL покрывает 100% узлов, которые были в внешних письмах.
3. **Визуальная система.** Hero-паттерн, карточка работы, палитра на основе реальных фото (не decorative SVG). *Зависимости:* шаг 1 (нужны реальные ассеты для дизайна). *Риск:* средний. *Готово когда:* Figma/прототип согласован с Ольгой и Далером.

5. **Миграция контента.** Донаполнить `ancestors`, `cultural-neuro-code`, заменить плейсхолдер `sound-brain`, прогнать `registry:sync`. *Зависимости:* шаг 1. *Риск:* низкий, но трудоёмко (реальные материалы у Ольги/Далера). *Готово когда:* `npm run audit` не показывает пробелов на флагманских узлах.
6. **QA.** Повторить аудит §3 на новом UI, включая `prefers-reduced-motion`, клавиатурную навигацию, lazy-loading, `npm run build` bundle-size. *Зависимости:* шаг 4. *Риск:* низкий. *Готово когда:* чеклист §8 закрыт.
7. **Deployment.** Обновлённый `sitemap.xml`, проверка `?id=`-редиректов в проде, только с отдельного разрешения владельцев. *Зависимости:* все предыдущие. *Риск:* высокий (публичный домен) — требует явного да/нет от Ольги и Далера перед деплоем.
