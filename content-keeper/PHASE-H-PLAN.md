# Phase H — Content enrichment plan

## Context

Структура лотоса зафиксирована в `feature/lotus-restructure` (commit `1d26bbe`). 174 узла, 0 orphans. Теперь нужно **наполнить** контентом — превратить stubs в готовые страницы и довести существующие до того же стандарта.

## Two audiences in scope

Каждая страница должна работать на двух читателей одновременно:

1. **Ивент-агентства / организаторы мероприятий** — им нужно понять: можно ли с нами связаться, какой масштаб, какие форматы возможны, кто уже доверял. Хотят увидеть надёжность, проведённые работы, отзывы.
2. **Кураторы — выставок, фестивалей, арт-премий** — им нужно увидеть: это **sci/tech-art с концепцией**, а не аттракцион. Хотят увидеть методологию, художественную линию, родство с другими практиками, проф. рецепцию.

**Общая рамка обоим**: это serious sci/tech-art с производственной зрелостью. Не wellness, не шоу, не «иммерсивное развлечение».

## Tone rules (write to)

- **Концепция первая, технология вторая**. На любой странице сперва — что мы исследуем/высказываем. Потом — как реализовано.
- **Без жаргона арт-теории первой строки**. Концепцию формулируем понятно, потом можно вглубь.
- **Без слов wellness, fun, magic, immersive experience** в маркетинговом смысле. «Immersive» только в техническом значении (multi-screen, BCI feedback и т.п.).
- **Конкретика > эпитеты**. Не «уникальный проект», а «4-канальная BCI-синхронизация на 8 человек, premiere 2025 в МФТИ».
- **Provenance видна с порога**. Где показано, кто заказал, какие пруфы — должны быть chip-ссылками вверху, не закопаны.

## Walk order

Итеративно, по веткам. Каждую ветку **закрываем целиком** перед переходом к следующей. Внутри ветки порядок: хаб-страница → flagship-узлы → остальные.

## Per-branch session — process

Каждая сессия = одна ветка.

1. **Я подгружаю срез ветки** через `npm run audit:checklist <branch>` (новый инструмент, см. ниже).
2. **Иду по узлам в порядке приоритета**.
3. На каждом узле:
   - Я готовлю **draft frontmatter + body EN + RU** на основе:
     - текущего контента (если есть),
     - parent / siblings / связанных узлов (provenance),
     - известных фактов из других мест базы (engagements.yaml, proofs.yaml, …).
   - Я показываю тебе draft + контекст (1-2 экрана).
   - Ты принимаешь, правишь, отвергаешь.
   - Применяю через Edit.
4. После ветки — `npm run audit && npm run audit:checklist <branch>` чтобы видеть прогресс.

## Per-node content shape

Минимум для каждого узла, чтобы считать «done»:

### Hub (категорийная страница)

- `title_en / title_ru` — без placeholder'ов
- Body EN: 2-3 абзаца — что в этой категории, какой принцип объединения, что выделено внутри.
- Body RU: то же
- **Не дублируем список детей** — он рендерится автоматически через provenance/Lotus grid.

### Product (произведение)

- `title_en / title_ru / shortTitle` если длинный
- `kind: product`, `subkind` из taxonomy
- `presented_at: [...]` — где показывался
- `proofs: [...]` — пруфы про этот продукт
- `media: [...]` — встроенные media-ассеты (минимум 1 изображение/видео)
- Body **EN + RU** структурой:
  - **Hook** (1 предложение) — что это в одной фразе.
  - **Concept** (1 абзац) — какую идею/исследование воплощает.
  - **Method** (1 абзац) — технологический субстрат, инструменты.
  - **Track** (1-2 строки) — где первая премьера, на каких событиях шло.
  - **Inline media**: 1-3 `![[media:...]]` или embed-ссылки.

### Event

- `title_en / title_ru`
- `kind: event`, `subkind` корректный
- `date_start`, `venue`
- `organizer: [...]` — кто хост
- `client: [...]` если коммерческий заказ
- `products: [...]` — что показывали
- `proofs: [...]` если есть
- `media: [...]` — фото/видео
- `attendance: { visitors, contacts }` если есть цифры
- Body: 1-2 абзаца — формат, контекст, что показано, как прошло.

### Proof

- `title_en / title_ru`
- `kind: proof`, `subkind` (award / letter / testimonial / press)
- `proof_of: [...]` — к какому продукту/событию относится
- `issued_by: [...]` — кто выдал/опубликовал
- `publication`, `publication_date` для прессы
- `asset` — путь к скану/файлу
- `quote_en / quote_ru` для testimonial
- Body: 1 абзац — что это за пруф, в каком контексте.

### Organizer

- `title_en / title_ru`
- `kind: organizer`, `subkind` (university / corporate / venue / gov / media / curator)
- `website`
- Body: 1-2 абзаца — что за организация, какой контекст работы с нами.

### Media-work

- `title_en / title_ru`
- `kind: media`, `subkind` (photo / video / sketch / poster / …)
- `about: [...]` — что документирует
- `image` / `media_url`
- Body: краткая подпись.

## Tooling — checklist generator

Новый скрипт `scripts/audit/dump-checklist.js`:

- Параметр: ветка (id хаба, опционально — `--all`).
- Walk subtree от хаба.
- На каждом узле проверка против per-kind shape (см. выше).
- Output: `content-keeper/PHASE-H-CHECKLIST-<branch>.md` с таблицей:

| id | type/kind | done? | missing fields | body words |
|---|---|---|---|---|
| schrodinger | product | 🟡 | media, proofs | 142 |
| ancestors | product | 🔴 | kind, subkind, body, presented_at, media | 12 (stub) |

- Status flags:
  - 🔴 stub (body < 50 слов или содержит «Stub»)
  - 🟡 partial (есть body, но не все нужные frontmatter поля)
  - 🟢 done (все обязательные поля + body ≥ 100 слов EN/RU)

- npm-скрипт: `audit:checklist`.

## Drafting protocol (как я подаю draft)

Каждый узел подаётся в формате:

```
─── node-id ─── current status
parent: ...
kind/subkind: ...
related: [parent siblings: a, b, c | upstream: hub-X]
existing body (если есть, чтобы не потерять смысл): "..."

PROPOSED frontmatter changes:
+ presented_at: [...]
+ media: [...]

PROPOSED body EN:
[draft]

PROPOSED body RU:
[draft]
```

Ты отвечаешь:
- «ок» → применяю as-is
- «правки: ...» → перерабатываю
- «пропусти» → ставлю в TODO

## Stopping criteria

- Все 174 узла имеют **status 🟢** в чек-листе (или явный TODO с причиной отложки).

- `npm run build` clean.
- Spot-check в браузере: 5-10 страниц рендерятся с заполненными provenance-секциями.
