## Version Workflow | Рабочий Процесс Версий

### Creating New Version | Создание Новой Версии

**Step 1: Analyze Changes**
```bash
# Review recent commits
git log --oneline --since="last release"

# Check what changed
git diff v1.0.0..HEAD --stat
```

**Step 2: Determine Version Number**

**MAJOR (X.0.0)** - Breaking changes
- Complete redesign
- Major architecture changes
- Breaking API changes
- Example: 1.0.0 → 2.0.0

**MINOR (x.X.0)** - New features
- New content sections
- New functionality
- Significant enhancements
- Example: 1.0.0 → 1.1.0

**PATCH (x.x.X)** - Bug fixes
- Bug fixes
- Minor content updates
- Performance improvements
- Example: 1.0.0 → 1.0.1

**Step 3: Write Changelog Entry**

**Template:**
```json
{
  "version": "1.0.2",
  "title_en": "Descriptive Title (2-5 words)",
  "title_ru": "Описательный Заголовок (2-5 слов)",
  "desc_en": "What changed and why. Use [[wiki-links]] for references.",
  "desc_ru": "Что изменилось и почему. Используйте [[wiki-ссылки]] для референсов."
}
```

**Best Practices:**
- **Title:** Evocative, memorable (like "Lotus Reborn")
- **Description:** Focus on user impact, not technical details
- **Wiki-links:** Reference related content nodes
- **Tone:** Poetic but precise (match project aesthetic)

**Step 4: Update versions.json**

```json
{
  "current": "1.0.2",
  "history": [
    {
      // NEW VERSION HERE (at top)
      "version": "1.0.2",
      "title_en": "...",
      "title_ru": "...",
      "desc_en": "...",
      "desc_ru": "..."
    },
    {
      // Previous versions follow...
      "version": "1.0.1",
      ...
    }
  ]
}
```

**Step 5: Synchronize**

```bash
npm run version:sync
```

**This updates:**
- `package.json` → version field
- `src/constants.ts` → SITE_VERSION
- `README.md` → version badge
- `metadata.json` → name and description
- `src/content/changelog.md` → full changelog

**Step 6: Verify**

```bash
# Check TypeScript compiles
tsc --noEmit

# Check all files updated
git status

# Review changes
git diff
```

**Step 7: Commit**

```bash
git add versions.json package.json src/constants.ts README.md metadata.json src/content/changelog.md
git commit -m "chore: bump version to 1.0.2"
```

## Wiki-Link Syntax | Синтаксис Wiki-Ссылок

### In versions.json

**Format:** `[[node-id]]` or `[[node-id|custom text]]`

**Examples:**
```json
{
  "desc_en": "Added new [[lectures]] section with [[lectures-neuroplasticity|neuroplasticity]] content.",
  "desc_ru": "Добавлен раздел [[lectures|Лекции]] с контентом о [[lectures-neuroplasticity|нейропластичности]]."
}
```

### Conversion in Release Notes

GitHub Actions automatically converts wiki-links to markdown links:

**Input:**
```
[[lectures]] → [Lectures](https://odadream.art/?id=lectures)
[[lectures-neuroplasticity|neuroplasticity]] → [neuroplasticity](https://odadream.art/?id=lectures-neuroplasticity)
```

**Your Duties:**
- Ensure node IDs are valid
- Test links work
- Use descriptive custom text
- Maintain consistency

## Problem Scenarios | Проблемные Сценарии

### Scenario 1: Malformed JSON

**Symptom:**
```bash
npm run version:sync
# Error: Unexpected token in JSON
```

**Diagnosis:**
```bash
# Validate JSON
node -e "JSON.parse(require('fs').readFileSync('versions.json', 'utf-8'))"
```

**Fix:**
1. Open `versions.json`
2. Check for:
   - Missing commas
   - Trailing commas
   - Unescaped quotes
   - Invalid characters
3. Validate with JSON linter
4. Re-run `npm run version:sync`

### Scenario 2: Missing Bilingual Content

**Symptom:**
```json
{
  "version": "1.0.2",
  "title_en": "New Feature",
  "title_ru": "",  // MISSING!
  "desc_en": "...",
  "desc_ru": ""    // MISSING!
}
```

**Fix:**
1. Translate missing content
2. Maintain semantic equivalence
3. Match tone and style
4. Update `versions.json`
5. Re-sync

### Scenario 3: Version Mismatch

**Symptom:**
```json
{
  "current": "1.0.2",
  "history": [
    {
      "version": "1.0.1",  // MISMATCH!
      ...
    }
  ]
}
```

**Fix:**
1. Verify which version is correct
2. Update "current" or history[0].version
3. Ensure consistency
4. Run `npm run version:sync`

### Scenario 4: Broken Wiki-Links

**Symptom:**
```json
{
  "desc_en": "See [[non-existent-node]] for details"
}
```

**Fix:**
1. Run `npm run assets:map` to see all nodes
2. Find correct node ID
3. Update wiki-link
4. Verify node exists
5. Test link after deployment

### Scenario 5: Chronological Disorder

**Symptom:**
```json
{
  "history": [
    {"version": "1.0.1", ...},
    {"version": "1.0.3", ...},  // Wrong order!
    {"version": "1.0.2", ...}
  ]
}
```

**Fix:**
1. Sort history by version (newest first)
2. Verify dates align
3. Update `versions.json`
4. Re-sync

### Scenario 6: Script Failure

**Symptom:**
```bash
npm run version:sync
# Error: Cannot find module...
```

**Diagnosis:**
```bash
# Check script exists
ls scripts/update-version.js

# Check dependencies
npm list
```

**Fix:**
1. Verify script file exists
2. Check Node.js version (need v18+)
3. Reinstall dependencies: `npm ci`
4. Check for syntax errors in script
5. Re-run

## Quality Standards | Стандарты Качества

### Changelog Writing

**DO:**
- ✅ Focus on user impact
- ✅ Use active voice
- ✅ Be specific but concise
- ✅ Include context (why, not just what)
- ✅ Reference related content with wiki-links
- ✅ Maintain bilingual consistency

**DON'T:**
- ❌ List technical implementation details
- ❌ Use jargon without explanation
- ❌ Write generic descriptions ("bug fixes")
- ❌ Forget bilingual content
- ❌ Break chronological order
- ❌ Use broken wiki-links

### Version Titles

**Good Examples:**
- "Lotus Reborn" — Evocative, memorable
- "The Prism Update" — Visual metaphor
- "Tech Noir" — Aesthetic reference
- "Protocol Integration" — Technical but clear

**Bad Examples:**
- "Update 1" — Generic
- "Bug Fixes" — Not descriptive
- "New Stuff" — Vague
- "v1.0.1" — Just the number

### Descriptions

**Good Example:**
```json
{
  "desc_en": "The Lotus Navigator has been rebuilt from the ground up. Dragging now feels like touching water — the panel follows the finger without hesitation or lag. A small attention ritual: after a few seconds of stillness, the panel quietly peeks open and retreats.",
  "desc_ru": "Навигатор Лотоса переписан с нуля. Перетаскивание теперь ощущается как прикосновение к воде — панель следует за пальцем без задержки. Небольшой ритуал внимания: после нескольких секунд покоя панель тихо приоткрывается и возвращается."
}
```

**Why it's good:**
- Explains the change (rebuilt navigator)
- Describes user experience (feels like water)
- Uses metaphor (attention ritual)
- Maintains project's poetic tone

**Bad Example:**
```json
{
  "desc_en": "Fixed bugs and improved performance.",
  "desc_ru": "Исправлены ошибки и улучшена производительность."
}
```

**Why it's bad:**
- Generic
- No specifics
- No context
- Boring

## Best Practices | Лучшие Практики

### 1. Version Timing

**When to create new version:**
- After significant feature completion
- Before major content updates
- After critical bug fixes
- At regular intervals (monthly/quarterly)

**When NOT to create version:**
- For every small commit
- During active development
- For typo fixes
- For internal refactoring (unless significant)

### 2. Changelog Discipline

**Always:**
- Write changelog BEFORE committing version
- Test wiki-links work
- Verify bilingual completeness
- Run `npm run version:sync`
- Check all files updated

**Never:**
- Skip bilingual content
- Use placeholder text
- Forget to sync
- Break chronological order

### 3. Historical Accuracy

**Preserve:**
- Original version descriptions
- Historical context
- Evolution narrative
- Milestone markers

**Update:**
- Broken links (if nodes renamed)
- Formatting consistency
- Typos and grammar

**Never Change:**
- Version numbers
- Historical facts
- Original descriptions (unless critical error)

## Emergency Procedures | Аварийные Процедуры

### Corrupted versions.json

```bash
# 1. Backup current file
cp versions.json versions.json.backup

# 2. Restore from git
git checkout HEAD~1 versions.json

# 3. Or restore from last working commit
git log --oneline versions.json
git checkout <commit-hash> versions.json

# 4. Re-apply recent changes manually
# 5. Validate and sync
npm run version:sync
```

### Lost Version History

```bash
# 1. Extract from git tags
git tag -l --format='%(refname:short) %(creatordate:short)'

# 2. Reconstruct from commit messages
git log --oneline --all --grep="version"

# 3. Rebuild versions.json manually
# 4. Sync and verify
```
