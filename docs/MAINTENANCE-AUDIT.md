# Аудит обслуживаемости ODA.dream V2

12 октября 2026 · исходная версия `903cb44` · статус: обследование завершено, изменения архитектуры предложены.

Проверен рабочий проект **odadream-site-v2**, а не соседний V1 с React/Lotus. Основание: исходники, импорты, сборочные скрипты, проверки, документы, история трёх последних пакетов и локальные измерения. Контекстная база здесь — инструкции, контракты, планы и реестры V2 и их ссылки на источники; внутреннее устройство Golem/Obsidian и аналитического hub не обследовалось. Это аудит разработки и сопровождения, не повторный аудит художественного содержания и не разрешение публикации.

## Вывод

Ощущение замедления обосновано. Основная нагрузка — длинный обязательный цикл проверок, связность шаблонов и каталога, ручная синхронизация нескольких документов и накопленный миграционный контекст. Сам объём публичного каталога пока не требует смены платформы или серверной CMS.

Сохраняем Astro, статическую публикацию, стабильные ID/маршруты, RU/EN, общие компоненты и токены. Сохраняем раздельные DEV/PUBLIC, разрешения на медиа и исключение внутренних сведений из сборки. Упрощаем устройство и рабочие процедуры внутри этих границ.

Статусы будущих работ ведём **только в [PROJECT-BACKLOG.yaml](PROJECT-BACKLOG.yaml)**. Этот документ содержит основания и порядок рефакторинга. Процент прежней миграции и авторская приёмка дизайна/текстов не пересчитываются по этому аудиту.

## Находки и предлагаемые изменения

**1. Один дорогой контроль для любого изменения.** `AGENTS.md:19` и README требуют весь цикл перед коммитом. `playwright.config.ts:7` задаёт `workers: 1`. `alignment.spec.ts:23–30` проверяет все страницы в 13 ширинах и двух темах; `design-rollout.spec.ts` дополнительно обходит канонические страницы, пилот имеет собственную матрицу. Эти проверки ловят реальные ошибки, но цена глобальной проверки платится и за локальную правку. Конфигурация E2E сама не строит PUBLIC: `public-build.spec.ts` использует существующий `dist`, поэтому отдельный ручной запуск E2E может проверить прежнюю сборку.

Предлагается единый запуск с уровнями `quick`, `full`, `release` и явной подготовкой нужного артефакта. `quick` выбирает проверки по изменённым файлам и зависимым семействам страниц; при неизвестной зависимости переходит к полному набору. Общие токены, маршруты и публикационная проекция всегда расширяют охват. `full` сохраняет весь нынешний контроль перед интеграцией/общей приёмкой; `release` проверяет **тот же артефакт**, который будет публиковаться. Подготовку результатов и команды переносим из разовых `.local-server/.../validate.mjs` в поддерживаемый скрипт. Увеличение worker — только после устранения фиксированных портов и разделения общих серверов. Механически ставить 4 worker сейчас рискованно.

**2. Инструментальный загрузчик стал тяжёлой зависимостью.** `scripts/site-data.mjs:9–25` транспилирует TS и рекурсивно встраивает зависимости в base64 `data:` URL. Кэш есть внутри процесса, но не между процессами unit-файлов; вызовы загрузчика встречаются в нескольких E2E-файлах при их сборе. Читаемый стек частично восстановлен, однако транспорт модулей остаётся громоздким.

Заменить этот транспорт на обычные ESM-файлы в игнорируемом кэше или совместимый TS-runner. Сначала маленький сравнительный прототип без замены всех проверок. Ключ кэша включает версии инструмента, параметры компиляции и весь граф исходников. Два режима каталога задаются явно; результат после правки зависимости не должен браться из старого кэша. Node native TS — возможный вариант, но текущие импорты без расширений и `import.meta.env` не позволяют просто удалить helper. Не переносим Vite/Astro-специфику в общий доменный слой.

**3. Активные документы перестали быть короткими контрактами.** `CONTENT-AND-CMS`, `DESIGN-GUIDE`, `DESIGN-AUDIT-PLAN`, `SITE-PRINCIPLES` содержат датированные добавления одного изменения. README одновременно описывает загрузку `/legacy-map.json` при `?id=` и её отсутствие в публичном runtime; там осталось 41 событие при 42 в данных. В бэклоге есть done-задачи с notes о ещё не подтверждённом VK, хотя позднее профиль внедрён в общей задаче футера. Это исторические записи, но без явного отделения их легко принять за действующие ограничения.

Нужна одна карта ответственности в README: принципы продукта → `SITE-PRINCIPLES`; поля/публикация/подготовка → `CONTENT-AND-CMS`; компоненты → `DESIGN-GUIDE`; роли токенов → `DESIGN-TOKENS`; задачи → backlog; авторские решения по текстам → register. Завершённые аудиты/миграционный план пометить историческими и читать по необходимости. Подробные протоколы проверок хранить как артефакты, а не дописывать в каждый контракт. В активных документах заменить повторённые описания ссылками; не удалять решения и свидетельства. Не создавать новую папку с ещё одним комплектом инструкций. Машинные inventory и реестры читать запросами/фильтрами; не загружать 1,4 МБ JSON целиком в контекст агента. Для начала/продолжения задачи генерировать из существующих источников короткую карточку: корень V2, task ID, принятое решение, текущая стадия, нужные контракты/файлы и критерии проверки. История всей переписки не должна быть обязательным источником состояния; отдельный вручную синхронизируемый handoff-план не нужен.

**4. Большой диспетчер страниц связывает разные задачи.** `PageView.astro` содержит ветви home/works/technology/recognition/education/programme/cooperation/studio/cases/contact, локальные тексты, выборки и разметку. `BaseLayout.astro` совмещает метаданные, навигацию, выходные данные, диалог медиа и поведение интерфейса. Общие карточки уже выделены — это хорошая основа, а не повод заново построить компонентную систему.

Разделить PageView на представления **по семействам страниц**, оставить небольшой типизированный dispatcher. Выборки/подготовку полей держать рядом с соответствующим семейством, общие компоненты сохранить. Начать с одного overview, затем одной detail-страницы; для каждой подтвердить неизменность URL, якорей, порядка чтения и визуальных осей. Из BaseLayout выделять самостоятельные Colophon/Header/MediaViewerShell и их контроллеры по необходимости, без дробления каждого абзаца в отдельный компонент. Глобальная замена всех шаблонов одним коммитом не нужна.

**5. Данные организованы по истории миграции.** `site.ts` одновременно определяет базовые типы, исходные записи, объединение дополнений, обратные связи и выборки. 44 декларации импортируют из него типы; есть повторение `isRealizedWork` в `site.ts` и `publication-scope.ts`. `additional-works`, `additional-events`, `*-details`, `archive-*` отражают происхождение, но редактирование одной работы требует поиска нескольких слоёв. Число `.find()` при нынешнем каталоге не является доказанной проблемой производительности.

Вынести независимые типы/схемы в доменные модули; группировать редакторские записи по Work/Programme/Event/Recognition, а происхождение хранить полями и ссылками. Сборку каталога и вычисляемые обратные связи оставить явными и детерминированными. Прямые ID-связи проверять, неизвестные ID не подменять молча главной/пустым slug. Существующая `CMS-01` остаётся одной задачей дальнейшей Content Collections: сначала пилот, затем решение по удобству редактирования, валидации и стоимости. База данных, GUI-CMS и переход на другой фреймворк этим аудитом не обоснованы.

**6. Проверки текущего сайта связаны с завершённой миграцией.** `verify-content.mjs:69` читает большой inventory; конец скрипта проверяет применение всех 238 ID к текущему публичному корпусу. В середине соседствуют обязательные языковые поля, отношения сущностей, права, исторические назначения файлов, хэши документов и готовность подготовленных медиа. Всё необходимо в подходящем контексте, но нынешняя связка требует вспоминать миграцию даже при текущей разработке.

Разделить набор на валидаторы `schema / relations / publication / prepared-assets / provenance`. Обычный контентный контроль использует актуальные данные и необходимые разрешения; архивный контроль вызывается при изменении источников/решений и полным выпускным набором. Связи опубликованных материалов с первоисточниками и проверка разрешений не исчезают. Большой исторический inventory остаётся воспроизводимым свидетельством; компактный текущий индекс можно **генерировать из него**, не редактировать параллельно. `publication-scope.ts` делить последним, под защитой тестов редактирования/прав/скрытых зависимостей.

**7. Глобальная таблица стилей расширяет область риска.** В `global.css` находятся и базовая геометрия, и hero, карточки, документы, паспорт, галереи; `reading.css` и `annotations.css` уже разделены по функции. Имеются 179 уникальных CSS-переменных в styles: число само по себе не означает избыточности, повторные определения нужны для тем/профилей. Удаление токена только потому, что простой поиск не нашёл `var()`, небезопасно: бывают JS-доступ и профильные значения.

Разделить стили на reset/base, общий layout и стили семейств компонентов, сохранив порядок каскада и действующие токены. Сначала перенос без изменения внешнего вида; затем отдельные изменения ролей/значений. Документация токенов описывает назначение и область применения, а таблицу фактических значений можно строить из CSS. Не токенизировать каждое число ради формального единообразия. Проверять обе темы, ширины около breakpoint, увеличение шрифта, длинные названия и состояния focus/hover.

**8. Контроль и отчётность зависят от ручной синхронизации.** В E2E реестр ожидается ровно 304 единицы, события ровно 42; при добавлении корректного материала меняются тесты и документы. Для завершённого миграционного снимка фиксированное число оправдано; для живого каталога нужен список стабильных обязательных ID + проверка отображения всей текущей выборки, а не новое число вручную. Нельзя строить expected только той же функцией, которую проверяем: сохраняются независимые примеры и инварианты. CI verify делает полный E2E, deploy — нет; связь разрешения публикации с успешно проверенным **тем же commit/artifact** должна стать явной до будущего выпуска.

У редакционного реестра есть дополнительный риск актуальности: `baseline_sha256` записан, но `scripts/editorial-register.mjs` проверяет структуру статусов, наличие даты/прохода/решения и полноту блоков, не соответствие текущему тексту. `EditorialWorkspace.astro` рассчитывает прогресс из этих сохранённых статусов. После последующей правки отметка проверки сама не инвалидируется. Нужен отпечаток **редакции, которая была проверена или принята**, и вычисляемое предупреждение о расхождении/повторной проверке. Решения владельца сохраняются с версией текста; изменение текста не объявляет новую редакцию принятой. Это риск механизма, не утверждение, что нынешние 304 единицы уже ошибочно согласованы.

**9. Локальное окружение имеет скрытые различия.** Windows-ярлык выбирает встроенный Node, терминал — системный, CI — Node 24. Контекст этой сессии указывает cwd соседнего V1, хотя рабочая задача относится к V2: инструкции React/Lotus нельзя автоматически переносить в Astro. DEV/PUBLIC используют фиксированные порты и собственный watcher с пересборкой, предыдущей безопасной версией и блокировкой параллельного запуска. Эти свойства полезны; переносить их в новую инфраструктуру без причины не следует. Launcher проверяет идентичность серверов, но Playwright `reuseExistingServer` сам по себе подтверждает доступность URL, не принадлежность процесса нужному проекту. При прошлой работе приходилось восстанавливать отсутствовавшие Git-объекты; текущий `git fsck --full --no-reflogs` завершился успешно, вывел только dangling commits — это не сообщение о повреждении. Репозиторий расположен в синхронизируемой папке; причинность прежних ошибок не установлена.

Добавить одну команду диагностики: корень/идентичность проекта, подходящий Node/зависимости, идентичность серверов, порты, свежесть PUBLIC, доступность подготовленных файлов. Зафиксировать поддерживаемый runtime для терминала/CI и проверку идентичности перед повторным использованием DEV в тестах. Отдельно подготовить проверяемую резервную копию и оценить рабочий checkout вне активной синхронизации; переносить его только после проверки .git, незакоммиченных изменений и нужных игнорируемых медиа-кэшей. Старую папку не удалять, публичные исходники и внешние пути не переписывать автоматически.

## Приоритет и порядок

Оценка `(влияние + риск) × (6 − трудоёмкость)`, шкалы 1–5. Это порядок обслуживания, не оценка качества художественного дизайна. Дни — ориентир объёма инженерной работы, не обещание календарного срока; этапы уточняются после первого замера.

Этап 4 не должен блокировать работу над контентом; формат хранения выбирается по результату пилота. Это 6 новых задач обслуживания и уточнение существующей `CMS-01`, а не новый параллельный бэклог.

## Как принять результат

- **Первый этап:** обычная локальная правка текста/компонента имеет одну команду проверки, понятный выбранный охват и ссылки на результаты. Цель quick — до 90 секунд на этой машине без подготовки медиа; неподходящее изменение явно расширяет набор. Полная матрица остаётся обязательной перед общей приёмкой. Цель времени — пока целевая, не достигнутый замер.
- **Документы:** при обычной реализации обновляются задача и один затронутый контракт; ещё один — только при изменении продуктового решения/публикационных правил. Отчёт о прогоне не копируется в 6–8 файлов. Новому агенту достаточно AGENTS/README, выбранной задачи и её контрактов; archive/inventory загружаются адресно.
- **Инструменты:** сравнить unit, content и сборку на одном commit/runtime минимум трижды; замерять время и память отдельно, не приписывать выигрыш всем причинам сразу. Ошибка выводит файл/поле/ID, не огромный data URL. Изменение зависимости инвалидирует кэш; чистый запуск воспроизводим.
- **Страницы/стили:** после каждого переноса совпадают маршруты, anchors, порядок чтения и семантические роли; сравниваем RU/EN, mobile/desktop, две темы, длинный контент и профильные изменения. Действующий дизайн не принимается автоматически по успешным тестам.
- **Данные/публикация:** тестовые restricted/draft/internal записи и их файлы отсутствуют в PUBLIC; неправильная ссылка/разрешение останавливает выпуск. Подготовленные страницы PDF остаются связаны с оригиналом и текстовыми копиями, приватный OCR не публикуется. Редактор может найти и изменить одну сущность без знания истории `additional-*`; изменение принятого текста показывает расхождение с проверенной редакцией, не переносит приёмку автоматически.
- **Надёжность:** восстановить checkout из резервной копии, построить тот же публичный пакет, сохранить и проверить нужные локальные кэши. До переноса никакие рабочие папки и Git-история не удаляются.

Предлагаемый первый пакет: `MAINT-CHECKS-01` + `MAINT-CONTEXT-01`, вместе с диагностикой runtime. Он даёт пользу до большого рефакторинга. До его исполнения действуют нынешние правила проверок; этот отчёт сам по себе их не отменяет.
