Цель: V2 становится основным проектом в `D:/YandexDisk/_ODA2/Сайт/odadream-site`, сохраняется история Git, на `odadream.art` публикуется проверенная V2. Текущий статус и приёмка — `RELEASE-GHPAGES-01` в PROJECT-BACKLOG.yaml. Этот документ описывает выполнение и восстановление, а не дублирует план миграции.

## Что установлено

- Основной checkout: `odadream-site`, ветка `codex/oda-v5-design-system`, есть изменённые и неотслеживаемые файлы. Их нельзя потерять при замене содержимого.
- V2: соседний Git worktree `odadream-site-v2`, ветка `codex/site-v2`. Общая `.git` физически находится в основном checkout; ещё существуют архивные worktree и worktree GDB. Переименование/подмена `.git` нарушит их связи.
- Опубликованный V1: `archive/published-site-v1.2.2`, commit `642bbb2`, папка `odadream-site-published-archive-2026-09-22`.
- Внутренний V1: `archive/site-v1.2.2`, commit `d4cb306`, папка `odadream-site-archive-2026-09-21`.
- `odadream-site-v1-backup-2026-09-22` содержит отдельные ZIP исходников и сборок обеих версий, V5 и прежние untracked-файлы. Это архив сентября; текущие изменения требуют нового снимка. Архивные checkout имеют изменения в генерируемых SVG: эталоном восстановления считаются Git refs и проверенные ZIP, а не состояние этих рабочих папок.
- После fetch удалённый `main` остаётся на `642bbb2`; локальный `main` `d4cb306` и опубликованный V1 являются предками V2. Для основной истории достаточно fast-forward. Другие ветки/теги сохраняются в общей `.git` и полном резервном bundle; переносить их файлы в V2 не требуется.

Первый Linux CI выявил зависимость тестового foreign-root от имени папки: `../odadream-site` совпадает с текущим checkout в CI. Исправлен только fixture на гарантированно другой дочерний путь; runtime identity guard продолжает отвергать любое несовпадение полного пути. Проверки допускают рабочую папку с будущим основным именем.
- GitHub Pages использует workflow, домен `odadream.art`, HTTPS включён. Репозиторий и DNS остаются прежними. В Actions custom domain определяется настройкой Pages; CNAME сохранён в публичной сборке для совместимости.

Репозиторий исходников публичный. Проверка девяти WorkDocument с `originalAccess: internal` показала: все их PDF уже есть в origin/main V1 и побайтно совпадают; новых внутренних оригиналов этого типа нет. Фильтрация V2 закрывает HTTP-доступ к ним и бюджетной странице в **сборке сайта**, но не скрывает старые Git-объекты. Полная сохранённая история не считается приватной копией. Ретроспективное закрытие уже опубликованных исходников потребовало бы отдельного решения; принадлежность GitHub organization к Free также не позволяет просто сделать Pages-репозиторий приватным без изменения схемы размещения/плана.

Проверяется байтовое равенство и HTTP 200. Это не перенос старых страниц/ID. URL домена и права на него в Search Console/Вебмастере сохраняются. После выпуска проверить чтение новой карты в обоих кабинетах; не удалять старую статистику. Неизвестные адреса V1 показывают предупреждение и ведут на главную по принятому правилу. Содержимое sitemap не смешивается с SPA V1.

Analytics Hub пока собирает V1. При переключении добавить отдельные sources V2 для новых property/counter и основного hostname; сохранить прежние источники/снимки как историю. Не переписывать IDs у сборщиков других сайтов и кампаний вслепую: `interference.odadream.art` использует собственный контекст. Проверить доступ Hub к обоим новым providers и его контрольный сбор после запуска сайта; admin-токены подготовки не копировать в публичный репозиторий или YandexDisk.

## Подготовка

1. Проверить свежие origin/main, GitHub Pages и статус текущих локальных серверов. Зафиксировать heads, branches/tags и SHA старого успешного Pages deployment.
2. Сделать независимые снимки текущих V1 и V2 вне YandexDisk: история, рабочие файлы, untracked, `.env*`, подготовленные тексты/медиа/OCR-кеш. Для V1 дополнительно сохранить полный `git bundle --all`; проверить SHA, manifest и bundle. Node modules и временные сборки восстанавливаются отдельно. Исходные материалы Obsidian/Golem/медиакита не перемещаются.
3. Проверить архивные ZIP на CRC и сохранить их SHA. Сохранить последний публичный artifact V1, если он ещё доступен; старые rebuilt dist в архиве не выдавать за байтовую копию последнего GitHub artifact.

Проверено 13.10: все пять ZIP целы, Git-комментарии трёх source/design ZIP совпадают с refs. Последний успешный GitHub run V1 `30387995050` уже не предоставляет скачиваемых artifacts. Восстановление опирается на точные исходники/refs и новую сборку с сохранёнными VITE variables; локальный archived dist остаётся дополнительной копией.
4. Выполнить `verify:release` с теми же PUBLIC_* значениями, которые передаёт deploy workflow. Проверить, что собранный JS содержит новые ID и включение аналитики, старых ID нет; DEV не попал в артефакт. Сборка, которую будут публиковать, должна пройти проверки после последнего изменения входов.
5. Получить зелёную CI-проверку V2 на Linux/Node 24. Push подготовительной ветки не запускает Pages: deploy слушает только main. Нельзя считать локальный Chromium доказательством Safari или отсутствующий CI-прогон — зелёным CI.

## Перенос в основную папку

Сохранять общую `.git` на месте. Перенос выполняется средствами Git и копированием локальных рабочих ресурсов, а не заменой двух папок целиком.

1. Остановить только идентифицированные DEV/PUBLIC этого проекта; не трогать другие worktree/процессы.
2. После проверки резервного снимка сохранить текущие изменения V1 отдельным локальным stash с untracked. Записать точный stash SHA. Ничего не сбрасывать через reset/clean и не отправлять private stash в удалённый репозиторий.
3. Создать ветку выпуска от проверенного head V2. В основном checkout переключиться на неё; `codex/site-v2` остаётся занята исходным worktree. Нужен чистый tracked/untracked checkout; игнорируемые старые env/build/node_modules не должны стать входами V2.
4. Сохранить необходимые игнорируемые файлы V1 в независимом архиве. Перенести локальную конфигурацию и нужные подготовительные кеши V2 в основную папку с проверкой SHA. Не копировать `.git`, React node_modules и старый dist. Перепривязать абсолютные пути приватных индексов/текстов; original sources остаются по прежним адресам.
5. `npm ci` с Node 24; проверить identity нового локального запуска, DEV/PUBLIC/реестр текстов и пути подготовки материалов. Обновить README и локальные инструкции: основная рабочая папка теперь `odadream-site`.
6. Повторить release-проверку в основном checkout. Сравнить содержимое с проверенной V2; служебные абсолютные пути и имена генерируемого CSS сами по себе не означают изменение содержимого, но подмена артефакта запрещена.
7. Только после успешного запуска основной папки вывести старый V2-worktree из активной разработки. Перед удалением/архивированием сохранить все нужные ignored-файлы. Остальные зарегистрированные worktree и архивные refs должны остаться рабочими.

## Публикация и контроль

1. Прямое решение владельца о выпуске должно относиться к конкретному проверенному head. Описание будущего сценария и проверка готовности сами по себе не считаются выполненной публикацией.
2. Перевести main на ветку выпуска через fast-forward; отправить обычный push в origin/main. Не применять force-push. CI ещё раз проверяет release и выкладывает именно проверенный dist.
3. Дождаться успешного Pages deployment. Проверить `/`, `/ru/`, `/en/`, работу, событие, образовательную программу, 404/старый `?id`, изображения и видео по HTTPS. Проверить DEV/редактор не доступны, SEO относится к V2, sitemap читается и HTTPS не перенаправляет циклически.
4. Проверить ноль запросов к аналитике до согласия; после согласия — новые GA4/Метрика, page_view и контрольные действия без дублей; после отзыва — остановка отправки. Наблюдать ошибки и данные после выпуска, учитывая задержку отчётов.
5. Внешние Search Console/Вебмастер: подтвердить обновление sitemap и отсутствие критических ошибок обхода. Сохранить URL CI/deployment, опубликованный SHA и фактическую дату выпуска в задаче.

## Восстановление

Причины восстановления: неуспешная доставка артефакта, неработающие основные страницы/ресурсы, утечка DEV или приватных материалов, некорректное согласие/отправка аналитики, неверные canonical/domain.

Не переписывать историю. Восстановить дерево опубликованного V1 из `archive/published-site-v1.2.2` отдельным новым коммитом поверх main либо повторно доставить проверенный архивный Pages artifact. Прежние VITE_* variables позволяют восстановить аналитику V1. Проверить домен/HTTPS и контрольные страницы повторно. Локальные изменения V1 возвращать из записанного stash/снимка только в отдельном архивном checkout; не накладывать их на Astro V2.

Первичные инструкции GitHub: [custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [custom domain](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site).
